# Deploying to Neon + Render

The database runs on **Neon** (PostgreSQL 18 + PostGIS 3.6). The API and the worker run on **Render**,
both built from `backend/Dockerfile` and defined in [`render.yaml`](../render.yaml).

```
Render web service  crisis-api     uvicorn, /api/v1      → Neon (app_citizen, app_public)
Render worker       crisis-worker  python -m app.worker  → Neon (app_worker, direct endpoint for LISTEN)
Render pre-deploy   alembic upgrade head                 → Neon (owner, direct endpoint)
```

## 1. Neon

1. The project runs **PostgreSQL 18** in **AWS US East 2 (Ohio)**. Render services must use the matching
   `ohio` region (set in `render.yaml`). Frankfurt would be closer to Cameroon; moving means a new Neon project.
2. Keep the default database (`neondb`) and its owner role. Copy two connection strings:
   - **Direct**: host without `-pooler`. Used for migrations, `app.manage` and the worker's LISTEN.
   - **Pooled**: host with `-pooler`. Optional for the API.
3. Create a second branch called `test` for integration tests, so tests never touch real data.

PostGIS is enabled by the first migration (`CREATE EXTENSION postgis`); no console step is needed.

## 2. Schema and roles (run once, from your machine)

```bash
cd backend
export MIGRATION_DATABASE_URL='postgresql://neondb_owner:...@ep-xxx.eu-central-1.aws.neon.tech/neondb?sslmode=require'
.venv/Scripts/python -m app.manage db-check      # versions, PostGIS availability
.venv/Scripts/alembic upgrade head               # schema + seed data
.venv/Scripts/python -m app.manage db-roles      # creates app_* roles, applies grants, prints their URLs ONCE
```

Store the printed URLs in Render (step 3) or a password manager. To replace lost passwords, run
`db-roles --rotate` and update Render.

## 3. Render

1. Push this repository to GitHub/GitLab.
2. In Render: **New → Blueprint**, select the repository. Render reads `render.yaml`.
3. Fill in the secret values it asks for:

| Service | Variable | Value |
|---------|----------|-------|
| crisis-api | `DATABASE_URL` | `app_citizen` URL (pooled host is fine) |
| crisis-api | `PUBLIC_DATABASE_URL` | `app_public` URL |
| crisis-api | `MIGRATION_DATABASE_URL` | owner URL, **direct** host |
| crisis-worker | `DATABASE_URL` | `app_worker` URL |

`TOKEN_PEPPER` is generated by Render. Never regenerate it: doing so breaks every report access token issued so far.

4. Deploy. Check `https://<api>.onrender.com/health` and `/ready`, then `/docs`, which stays enabled outside `APP_ENV=production`.

## Notes

- **Cost:** the pre-deploy command and background workers need paid Render instances (Starter).
- **Neon scale-to-zero:** the worker holds a LISTEN connection, so the compute stays awake while it
  runs. That is intended: reports must be processed promptly.
- **Owner credentials** sit only on `crisis-api`, for the pre-deploy migration. Runtime code uses the
  least-privileged roles.
- **Production:** set `APP_ENV=production` only after the go-live checklist (Engineering pack §14).
  It disables `/docs` and refuses development secrets.

## Staff sign-in (OIDC)

Staff routes (`/api/v1/incidents`, `/api/v1/review/...`, `/api/v1/auth/me`) accept access tokens from
any OpenID Connect provider (Auth0, Keycloak, Clerk, Microsoft Entra, ...). Until these are set they
answer 503 and nothing else is affected.

1. At the provider, create an **API / resource** whose identifier becomes the token audience, and a
   login application for the dashboard.
2. On the API service set `OIDC_ISSUER` (e.g. `https://tenant.eu.auth0.com/`, with the trailing slash
   exactly as in the provider's tokens) and `OIDC_AUDIENCE`. `OIDC_JWKS_URL` is optional.
3. Set `DASHBOARD_DATABASE_URL` to the `app_dashboard` URL that `db-roles` printed.
4. For each staff member, copy their provider user id (`sub`) and run, with the owner URL:
   `python -m app.manage grant --subject '<sub>' --email person@org reviewer`
   (`reviewer` = incident.view, assess, verify, correct, merge, report.review). Revoke with `--revoke`.

## Review dashboard (static site)

`dashboard/` is a Next.js app exported as static files. It signs reviewers in with Auth0 in the
browser (Authorization Code + PKCE, tokens in memory only) and calls the API directly.

1. In Auth0: **Applications -> Create Application -> Single Page Application** ("Sisay Review").
   In its Settings set Allowed Callback URLs, Allowed Logout URLs and Allowed Web Origins to the
   dashboard URL (e.g. `https://sisay-review.onrender.com`, plus `http://localhost:3000` for local
   work). Under **APIs -> Sisay API -> Machine to Machine / Application Access**, allow the new
   application to request tokens for the API if your tenant requires it.
2. In Render: **New -> Static Site**, repo as before, Root Directory `dashboard`, Build Command
   `npm ci && npm run build`, Publish Directory `out`. Environment: `NEXT_PUBLIC_API_BASE`,
   `NEXT_PUBLIC_AUTH0_DOMAIN`, `NEXT_PUBLIC_AUTH0_CLIENT_ID`, `NEXT_PUBLIC_AUTH0_AUDIENCE`
   (see `dashboard/.env.example`). Add the security headers listed in `render.yaml`
   (Settings -> Headers).
3. On the API service set `CORS_ORIGINS` to the dashboard URL (comma-separate several; exact match,
   no trailing slash). Without it the browser blocks the dashboard's requests.
